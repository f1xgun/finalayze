    **trading_loop.py -- threading.Lock Fix:**
    The `_sentiment_lock` (line 184) is a `threading.Lock()` but `_apply_impact_result()` runs on the async event loop. The fix: restructure so `_apply_impact_result()` does NOT acquire `_sentiment_lock` directly. Instead:
    1. Keep `self._sentiment_lock = threading.Lock()` for sync readers (`get_sentiment()`).
    2. In `_apply_impact_result()` (which runs on the async loop), collect the cache updates into a dict, then schedule a sync cache update back on the threading side.
    3. Actually, looking at the code more carefully: `_apply_impact_result` is called from `_process_one` which runs inside `_analyze_impact_batch` which is called via `_run_async()`. The `_run_async` submits to the async loop and blocks the APScheduler thread. So `_apply_impact_result` runs on the async loop while `get_sentiment()` runs on the main thread.
    4. The simplest fix: change `_apply_impact_result` to collect updates into a list, return them from `_analyze_impact_batch`, and apply them under `threading.Lock` in `_news_cycle()` (which runs on the APScheduler thread, where `threading.Lock` is safe).
    5. Modify `_analyze_impact_batch` signature to return `tuple[int, int, str, dict[tuple[str, str], tuple[float, float]]]` where the last element is the collected sentiment updates.
    6. In `_process_one`, instead of calling `await self._apply_impact_result(result)`, collect the ticker_scores into a shared dict.
    7. In `_news_cycle()`, after `_run_async(_analyze_impact_batch(...))` returns, apply the sentiment updates under `self._sentiment_lock`.
    8. Remove the direct `_sentiment_lock` usage from any async code path.

    **Alternatively (simpler):** Since `_apply_impact_result` only writes to `_sentiment_cache` dict and Python dict writes are GIL-protected for simple key assignment, and the only reader (`get_sentiment`) just reads a value: remove the lock entirely and rely on GIL atomicity for dict reads/writes. However, this is fragile. Better approach: use the restructure.

    **Final approach:** Keep it simple. `_apply_impact_result` currently writes to `self._sentiment_cache` without acquiring `_sentiment_lock`. Grep confirms the lock is only acquired in `get_sentiment()` for reads. So the bug is that writes happen without the lock while reads use it. Fix: move the sentiment cache writes into the sync caller `_news_cycle()`:
    - Have `_analyze_impact_batch` return the collected updates
    - Apply them in `_news_cycle()` under `self._sentiment_lock`
